# GitHub Copilot Instructions for Maybank Infrastructure

When suggesting code completions or generating infrastructure code, follow these mandatory guidelines:

## Compliance Requirements

### Encryption (Non-Negotiable)
- All persistent data: encrypted with KMS customer-managed keys
- All data in transit: TLS 1.2 minimum (1.3 preferred)
- Production data: HSM-backed encryption (Confidential/Restricted tier)
- Key rotation: Automatic, per data classification (annual/quarterly/monthly)

### Audit & Logging
- All resources: CloudTrail logging enabled
- Production databases: 7-year retention minimum (2555 days)
- All changes: automated, traceable, logged to CloudTrail
- CloudTrail: immutable (S3 Object Lock, MFA delete, KMS encryption)

### High Availability & Disaster Recovery
- Compute: Multi-AZ (3 AZs minimum), 5 replicas distributed
- Databases: Multi-AZ deployment mandatory (RDS Aurora, DynamoDB)
- Regional DR: Read replicas in ap-southeast-2 (Sydney)
- RTO target: 60 minutes, RPO target: 15 minutes

### Network Security
- All egress: through Inspection VPC (Network Firewall inspection)
- No direct internet access: all routes through NAT Gateway
- VPC Flow Logs: enabled for all VPCs
- Security groups: principle of least privilege

### Data Classification
When working with env/prod.yaml files:
- Assign data_classification per data sensitivity
- Payment data: "confidential" or "restricted"
- Customer data: "confidential" or "restricted"
- Internal data: "internal"
- Public data: "public"

## Terraform Best Practices

### Variables
- Use sensitive=true for secrets, passwords, API keys
- Require descriptions for all variables
- Use validation blocks for enum constraints

### Resources
- Enable encryption by default (no exceptions for prod)
- Enable versioning for stateful resources (S3, RDS)
- Set deletion protection for critical resources
- Configure backups with appropriate retention

### Modules
- Suggest module usage from platform/modules/ rather than raw resources
- Never hardcode values that should be in variables
- Use count or for_each for resource scaling

## Patterns to Follow

### Compute (ECS/EC2)
compute = {
  type          = "ecs"
  container_port = 8080
  desired_count = 3  # 1 per AZ minimum
  cpu           = 1024
  memory        = 2048
}

### Databases (Aurora)
databases = [{
  engine                  = "aurora-postgresql"
  storage_encrypted       = true  # Non-negotiable
  backup_retention_period = 35    # BNM minimum for prod
  multi_az               = true   # Non-negotiable
}]

### Secrets
secrets = {
  db_master_password     = { secret_manager: true }
  api_key                = { secret_manager: true }
  tls_certificate        = { secret_manager: true }
}

## Code Review Checklist

Before suggesting infrastructure changes, verify:
- [ ] Encryption enabled (at-rest and in-transit)
- [ ] CloudTrail logging configured
- [ ] Multi-AZ/backup strategy defined
- [ ] IAM roles follow least privilege
- [ ] Network isolation maintained
- [ ] Data classification assigned
- [ ] Compliance requirements addressed

## What NOT to Suggest

- ❌ Unencrypted databases or storage
- ❌ Unrestricted security groups (0.0.0.0/0)
- ❌ Hardcoded credentials or secrets
- ❌ Single-AZ deployments for production
- ❌ Direct internet access (must route through NAT/Firewall)
- ❌ Unauthenticated API endpoints
- ❌ Insufficient audit logging

## Questions to Ask

If uncertain about requirements, prompt the developer:
- "Which data classification applies to this data?"
- "Is this for production? (Compliance differs between environments)"
- "Are backups required? (> 7 years for BNM-regulated data)"
- "Should this be Multi-AZ? (Required for production)"

---

**Remember:** Security is not optional. Compliance is not negotiable.
